# 阶段 2 · 地基：依赖容器、配置、能启动的双进程

> **这一步要解决的事**：让"跑起来"不再靠运气——中间件在自己的 Docker 里起着、应用连得上、
> API 与 Worker 两个进程能分别启动、Redis 挂掉时不牵连启动。
> **做完能演示**：`curl localhost:8081/healthz` 返回 `{"status":"ok"}`；`docker compose stop redis` 后应用仍能启动。
> **本阶段不写任何业务代码。**

按顺序做，每一步末尾都有**通过标志**。没看到标志就停在原地解决，不要往下走——
后面每一步都建立在它前面那步已经成立的前提上。

## 第 2 步 · 起依赖容器（MySQL + Redis）

Java 版有自己的依赖清单，放在工程里，不借用原版仓库。新建 `deploy/docker-compose.yml`，内容如下
（MySQL 的参数与原版一致：宿主端口 3307、库名 `feedsystem`、密码 123456、utf8mb4；
这样将来想让原版也连同一个库时不用改任何配置）：

```yaml
name: feed-deps
services:
  mysql:
    image: mysql:8.0
    restart: always
    environment:
      MYSQL_ROOT_PASSWORD: 123456
      MYSQL_DATABASE: feedsystem        # 首次启动自动建这个库（空库，没有表）
      TZ: "Asia/Shanghai"
    ports:
      - "3307:3306"                     # 宿主 3307，容器内仍是 3306
    volumes:
      - mysql_data:/var/lib/mysql
    command:
      - --default-authentication-plugin=mysql_native_password
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_0900_ai_ci
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p123456 --silent"]
      interval: 5s
      timeout: 5s
      retries: 20

  redis:
    image: redis:7-alpine
    restart: always
    command: ["redis-server", "--appendonly", "yes", "--requirepass", "123456"]
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD-SHELL", "redis-cli -a 123456 ping"]
      interval: 5s
      timeout: 3s
      retries: 20

volumes:
  mysql_data:
  redis_data:
```

启动并验证。约定一次：本套文档里的 `docker compose` 命令**默认在 `deploy/` 目录下**执行；在工程根目录时把命令写成 `docker compose -f deploy/docker-compose.yml …`，两种等价（《04》的验收清单用的就是后者）：

```bash
cd deploy
docker compose up -d
docker compose ps                              # 期望 STATUS 两行都是 ... (healthy)
docker compose exec mysql  mysql -uroot -p123456 -e 'SHOW DATABASES;'   # 期望含 feedsystem
docker compose exec redis  redis-cli -a 123456 ping                     # 期望 PONG
```

Kafka 容器**这一步不装**，等你真的要用它的时候在《07》第 1 步追加进同一个文件。

三个以后每天都要用的操作（记在 `deploy/` 目录下执行）：

```bash
docker compose logs -f mysql      # 跟踪某个服务的日志（Ctrl-C 退出，不会停容器）
docker compose restart redis      # 只重启一个服务
docker compose down -v            # 彻底重置：连数据卷一起删——10 张表、缓存、消息全没了
```

> 警告：`down -v` 里的 `-v` 是"删数据卷"，执行前想清楚。日常停启用 `stop` / `start` 就够了，
> 它们不碰数据。

> 说明：原版仓库 `feedsystem_video_go-main/docker-compose.yml` 里也有一份 MySQL/Redis，
> 端口与这份完全相同，**两份不能同时运行**（谁后起谁报 `port is already allocated`）。
> 以后要做"两版对照测试"时不要起原版那份容器——让这份继续跑，原版只跑它的进程，
> 具体做法在《00》第 6 节（方案 A）。

**通过标志**：`docker compose ps` 两行都是 healthy，`SHOW DATABASES` 能看到 `feedsystem`，`ping` 返回 `PONG`。

## 第 3 步 · 认识这个库：空的，表要你自己建

```bash
docker compose exec mysql mysql -uroot -p123456 feedsystem -e 'SHOW TABLES;'
```

期望输出 `Empty set`。**这是正常的，也是本阶段最重要的一个认知**：

原版用 GORM，启动时调 `db.AutoMigrate(...)` 自动把 10 张表建出来。
Java 版用 MyBatis-Plus，它**只管读写，不会建表**（Flyway 之类的自动迁移工具我们也不引入，
理由是你需要知道自己库里有什么）。

所以：**每个阶段动手写代码前，第一件事是建那几个阶段用到的表**，DDL 就写在该阶段文档的第 1 步里：

| 表 | 在哪一步建 |
|----|-----------|
| `accounts` | 《03》第 1 步 |
| `videos`、`tags`、`video_tags`、`outbox_msgs` | 《04》第 1 步 |
| `comments`、`likes`、`notifications` | 《05》第 1 步 |
| `socials` | 《06》第 1 步 |
| `messages` | 《08》第 1 步 |

**通过标志**：看到 `Empty set` 并且明白它为什么是空的。

## 第 4 步 · 只配 MySQL，先把应用启动一次

打开 `src/main/resources/application.yml`（向导建的空文件），把下面两段写进去，**这一步只写两件事**：

> 说明：有的向导版本生成的是 `application.properties`。两份并存时以后查错会看花眼——
> 用 yml 就把那个 properties 删掉；`target/classes/` 下留下的同名文件是编译产物，不影响启动，
> `./mvnw clean` 会清掉。你这份工程现在只有空的 `application.yml`，直接写就行。

```yaml
server:
  port: 8081                  # Java 版端口；给最终顶替原版留了 8080

spring:
  datasource:
    url: jdbc:mysql://localhost:3307/feedsystem?characterEncoding=utf8mb4&connectionTimeZone=LOCAL&forceConnectionTimeZoneToSession&allowPublicKeyRetrieval=true&useSSL=false
    username: root
    password: ${MYSQL_ROOT_PASSWORD:123456}
    hikari:
      maximum-pool-size: 10
```

`${MYSQL_ROOT_PASSWORD:123456}` 的意思是：优先读同名环境变量，没有就用 `123456`。
"改配置不改代码"就是靠这个语法。

跑起来：

```bash
./mvnw spring-boot:run
```

期望日志末尾出现 `Tomcat started on port 8081` 和 `Started FeedAppApplication in ...`。
`mysql` 连接信息不对会在这里当场炸出来（见文末 FAQ），所以这一步同时也是对第 2 步的复查。

URL 里那几个参数的作用：`connectionTimeZone=LOCAL` + `forceConnectionTimeZoneToSession`
让"写进库的时间"和"从库里读出的时间"跟本机时区一致，否则整条时间线会按小时偏移
（阶段 6 的时间线游标、阶段 8 与原版共享缓存都会踩到）。原版 Go 驱动用的是同一意图的另一套写法：
`parseTime=True&loc=Local`——参数名不通用，意图通用。`allowPublicKeyRetrieval=true`
是 MySQL 8 默认加密方式下建立连接所需的开关。

**通过标志**：应用启动成功、监听 8081、没抛异常（先别 Ctrl-C，下一步直接用这个运行中的进程）。

## 第 7 步 · 连上 Redis，并把配置绑定成 Java 对象

`application.yml` 里**追加** Redis 与自定义段（`feed:` 是我们自己名字的键，Spring 不认识，下一步绑定）：

```yaml
spring:
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
      password: ${REDIS_PASSWORD:123456}
      timeout: 2s
      lettuce:
        pool:
          enabled: true

feed:
  redis:
    key-prefix: "v1:"          # 全项目 Redis key 的统一前缀，与原版共享缓存的前提
```

> 说明：不要在同一个文件里出现两个顶层 `spring:`——同名键的后一份会顶掉前一份
> （YAML 规范也允许解析器直接报错），于是第 4 步写好的 `datasource` 会莫名其妙消失。
> 正确做法：把 `data:` 直接接在已有 `spring:` 块的 `datasource` 下面。

`feed:` 开头的键要绑定成对象才用得上，新建 `config/AppProps.java`：

```java
@ConfigurationProperties(prefix = "feed")
public record AppProps(Redis redis) {
    public record Redis(String keyPrefix) {}
}
```

启动类上加一行：

```java
@EnableConfigurationProperties(AppProps.class)
```

> 说明：yml 里的 `key-prefix` 会自动映射到 `keyPrefix`（Spring 的松散绑定）。
> 后面每个阶段往 `feed:` 里加键时，同步给 `AppProps` 加一个嵌套 record：
> 阶段 3 加 `jwt`、阶段 7 加 `kafka` 和 `outbox`。现在写是空对空。

**通过标志**：重启无异常，且随便找处注入 `AppProps` 打印 `redis().keyPrefix()` 得到 `v1:`
（临时打在启动方法里即可，验完删掉）。

## 第 8 步 · 降级开关：Redis 挂了也要能启动

规则只有一条：**MySQL 是硬依赖，Redis / Kafka 是软依赖**。
MySQL 连不上不用你写代码——Hikari 建连失败会直接让进程起不来，行为天然正确。
Redis 需要你自己兜：

```java
@Component
public class FeatureFlags {
    private static final Logger log = LoggerFactory.getLogger(FeatureFlags.class);
    private volatile boolean cacheEnabled = true;
    private volatile boolean mqEnabled = true;   // 阶段 7 接上 Kafka 后才开始生效

    private final StringRedisTemplate redis;
    public FeatureFlags(StringRedisTemplate redis) { this.redis = redis; }

    @PostConstruct
    void probe() {
        try { redis.opsForValue().get("feed:probe"); }
        catch (Exception e) { cacheEnabled = false; log.warn("cache disabled: {}", e.getMessage()); }
    }
    public boolean cacheEnabled() { return cacheEnabled; }
    public boolean mqEnabled() { return mqEnabled; }
}
```

此后每个缓存读写点的第一行都是 `if (!flags.cacheEnabled()) return 兜底;`。现在验一次：

```bash
docker compose stop redis        # 在 deploy/ 下
# 重启应用 → 期望：能启动，日志有一行 cache disabled: ...
docker compose start redis       # 恢复
```

**通过标志**：Redis 停着应用照样起来，日志有 `cache disabled`。

## 第 9 步 · 拆出 Worker 进程

为什么两个进程：点赞落库这类"慢活"不该阻塞 HTTP 请求，独立进程还能单独重启。
这是后端系统的通用形态，不是原版的怪癖。

先把 `FeedAppApplication` 改名为 `ApiApplication`（IDEA 里 Shift+F6），再加 `WorkerApplication`：

```java
@SpringBootApplication
@EnableConfigurationProperties(AppProps.class)
@MapperScan("io.github.p_feed.**.mapper")
public class ApiApplication {
    public static void main(String[] args) { SpringApplication.run(ApiApplication.class, args); }
}

@SpringBootApplication
@EnableConfigurationProperties(AppProps.class)
@MapperScan("io.github.p_feed.**.mapper")
public class WorkerApplication {   // 用 worker profile 启动，见下
    public static void main(String[] args) {
        new SpringApplicationBuilder(WorkerApplication.class)
            .properties("spring.profiles.active=worker")
            .run(args);
    }
}
```

`application.yml` **末尾**追加一段（`---` 是同一个文件里的第二个文档，只在 worker profile 生效）：

```yaml
---
spring:
  config:
    activate:
      on-profile: worker
  main:
    web-application-type: none    # 不起 HTTP 端口
```

> 警告：现在工程里有**两个**带 `main` 方法的 `@SpringBootApplication` 类，
> `./mvnw spring-boot:run` 会报 `Unable to find a single main class` —— 这不是你做错了，
> 是 Maven 插件不知道该跑哪个。在 `pom.xml` 的 `spring-boot-maven-plugin` 里明确指定一次：
>
> ```xml
> <plugin>
>     <groupId>org.springframework.boot</groupId>
>     <artifactId>spring-boot-maven-plugin</artifactId>
>     <configuration>
>         <mainClass>io.github.p_feed.ApiApplication</mainClass>
>     </configuration>
> </plugin>
> ```

验收（API 走 pom 里指定的默认值，Worker 用插件参数临时覆盖主类，属性名是 `spring-boot.run.main-class`）：

```bash
./mvnw spring-boot:run
# 期望：Tomcat started on port 8081

./mvnw spring-boot:run -Dspring-boot.run.main-class=io.github.p_feed.WorkerApplication
# 期望：日志 Started WorkerApplication，且【没有】"Tomcat started"
```

> 说明：第二条命令不用再加 `-Dspring-boot.run.profiles=worker`——`WorkerApplication.main`
> 里已经用 `.properties("spring.profiles.active=worker")` 强制了。
> 打成 jar 之后同理：`java -jar target/feed-0.0.1-SNAPSHOT.jar` 起 API，
> `java -jar target/feed-0.0.1-SNAPSHOT.jar --spring.profiles.active=worker` 起 Worker（一个 jar 两种跑法）。

**通过标志**：worker 进程起来但不监听 8081，Ctrl-C 能停。

## 第 10 步 · RedisKeys：全项目唯一的拼 key 入口

阶段 4 起到处都是 Redis key，前缀写错一次的代价是"缓存永远不命中"这种查一天的 bug。
所以从现在起，**任何 key 只能经这个类拼出来**：

```java
@Component
public class RedisKeys {
    private final String prefix;                    // 注入 AppProps.redis().keyPrefix()
    public RedisKeys(AppProps p) { this.prefix = p.redis().keyPrefix(); }
    public String key(String fmt, Object... args) { return prefix + String.format(fmt, args); }
}
```

给它写一个单测（工程里已经有一个向导生成的空壳测试 `FeedAppApplicationTests`，你写的这个是第一个真正有断言的；
后面每个工具类都照这个套路）：

```java
@Test
void prefixApplied() {
    assertThat(new RedisKeys(new AppProps(new AppProps.Redis("v1:")))
        .key("video:detail:id=%d", 7)).isEqualTo("v1:video:detail:id=7");
}
```

两件同样推迟到《03》的事，现在写都是空对空：限流规则表 `RateLimits`（《03》第 1 步建，
那时才有第一个挂载它的接口）；错误映射 `infra/Errors.java` + `@RestControllerAdvice`
（《03》第 4 步做，那时才有第一个真正的业务异常）。

**通过标志**：`./mvnw test` 绿。

## 卡住了看这里

**启动报 `Failed to configure a DataSource`。**
原因：`application.yml` 不存在或没被读到（文件名拼错、放错目录）。
处理：确认在 `src/main/resources/application.yml`，且 `target/classes/` 里也有它。

**启动报 `Communications link failure`。**
原因：MySQL 容器没起，或者 URL 端口写成了 3306。
处理：`docker compose ps`；URL 必须是 **3307**。

**启动报 `Access denied for user 'root'`。**
原因：compose 里的密码和 yml 里的密码不是同一个值（比如你改了其中一边）。
处理：两处对照；`docker compose exec mysql mysql -uroot -p123456 -e 'select 1'` 能过说明容器这边是对的。

**`docker compose up` 拉镜像超时（`registry-1.docker.io` i/o timeout）。**
原因：本机到 Docker Hub 的网络不通。
处理：从公共镜像拉下来重打标签，compose 就会直接用本地镜像启动：

```bash
docker pull docker.1ms.run/library/mysql:8.0 && docker tag docker.1ms.run/library/mysql:8.0 mysql:8.0
```

`redis:7-alpine` 同理。个别镜像在 `1ms.run` 上取不到时换 `docker.m.daocloud.io` 试。
> 这些镜像站点随时可能失效；都取不到时就搜"docker 镜像加速"找当前可用的公共源，
> 做法都是 `docker pull <源>/library/<镜像>:<标签>` 再 `docker tag` 成官方名，compose 配置一行都不用改。

**`docker compose up` 报 `port is already allocated`。**
原因：原版仓库那份 compose 正在跑（3307/6379 被占），或者宿主机另有 MySQL/Redis。
处理：`docker compose ls` 看在跑的项目；`ss -lntp | grep -E '3307|6379'` 看端口被谁占了。

**curl localhost 返回 502 / 空。**
原因：终端走了代理（本机 `HTTP_PROXY` 指向 127.0.0.1:7890）。
处理：所有本机 curl 都加 `--noproxy '*'`，例如 `curl -s --noproxy '*' localhost:8081/healthz`。

**worker profile 启动后仍然监听了 8081。**
原因：`web-application-type: none` 写在了默认文档段而不是 `---` 之后的 profile 段。
处理：检查它在 `---` **之后**，且 `on-profile: worker` 拼写无误。

**`@MapperScan` 报找不到 mapper。**
原因：扫描路径和实际包名不一致（你的根包是 `io.github.p_feed`）。
处理：以真实包名为准改注解；这个错在阶段 3 写第一个 mapper 时必然撞上，先有印象。

**上传大文件报 `SizeLimitExceededException`（阶段 4 会遇到）。**
原因：Spring 默认 multipart 上限 1MB。
处理：那时再往 yml 加 `spring.servlet.multipart` 两行，见《04》。
