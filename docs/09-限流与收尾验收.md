## 第 1 步 · 限流规则表核对（五条，逐字）

| 规则段 | 限额 | 维度 | 挂载接口 |
|--------|------|------|----------|
| `account_register` | 5 / 小时 | IP | `POST /account/register` |
| `account_login` | 10 / 分钟 | IP | `POST /account/login` |
| `like_write` | 30 / 分钟 | 账号 | `/like/like`、`/like/unlike` |
| `comment_write` | 10 / 分钟 | 账号 | `/comment/publish`、`/comment/delete` |
| `social_write` | 20 / 分钟 | 账号 | `/social/follow`、`/social/unfollow` |

先核对再动手：这五条分散在三个阶段建的 `RateLimits.java` 里，此刻应当齐全且数值一字不差。

行为契约里有两个容易被写错的点，现在就记住：

- 未登录时按账号维度取不到 subject → **跳过限流**，不按 IP 兜底。
- IP 语义：不解析任何代理头（不信 XFF），直连场景等于 remoteAddr；将来上反代再统一处理（见文末"改了 vite"那条之前的问题 2）。

**通过标志**：`RateLimits.ALL.size() == 5`，五条的 limit/window/byIp 与上表逐格一致。

## 第 2 步 · 写限流拦截器（固定窗口 + fail-open）

文件摆放：`RateLimiter` 接口与 `RedisRateLimiter` 放 `infra` 包（和 `RateLimits` 同级），
`RateLimitInterceptor` 放《03》的 `web` 包（和 `JwtAuthInterceptor` 并列，注册进 `WebConfig`）：

```text
RateLimitInterceptor(preHandle)
  ├─ 按 URI 查 Map<String, RateLimiter> 找规则      ← 五条规则 = 五个 Bean
  ├─ RedisRateLimiter：Lua 计数 + fail-open
  └─ subject 取不到 → 直接放行（不 401、不限流）
```

```java
// 文件：io.github.p_feed.infra.RateLimiter
public interface RateLimiter {
    /** @return true=放行（含 Redis 不可用的 fail-open）; false=超限，由拦截器写 429 */
    boolean tryAcquire(String subject);
}
```

Spring MVC 没有"每个路由挂一个中间件实例"的便利，最直白的做法是拦截器里按 URI 前缀查表；
挂载清单就是第 1 步那张表，逐条抄进配置，别漏 `/like/unlike` 这类"看起来不像写"的接口。

Lua 只有三行，但每行都有理由：

```lua
local count = redis.call("INCR", KEYS[1])
if count == 1 then redis.call("PEXPIRE", KEYS[1], ARGV[1]) end
return count
```

- 用 `DefaultRedisScript<Long>` 走一次 EVALSHA 往返；`ARGV[1]` 传**毫秒**（窗口长度）。
- 只在 `count == 1` 时设过期——每次都重设的话，窗口会被无限往后推。
- IP 维度用 `request.getRemoteAddr()`（**不读 XFF**）；账号维度用登录态里的 accountID。
- 429 响应复用项目里的错误响应工具写 `{"error":"too many requests"}`，别手写 JSON 字符串。

四条既定事实（决定你测出来的现象）：

1. 算法是**固定窗口计数**：`INCR` + 首次 `PEXPIRE`（Lua 原子）。不是令牌桶——
   窗口交界处最多 **2 倍突发**（登录：前一分钟末 10 次 + 新一分钟初 10 次，都放行）。
2. key 逐字 `feedsystem:ratelimit:{规则}:{对象}`，对象是 IP 或 accountID——**没有 `v1:` 前缀**，
   它是全项目唯一不走缓存键封装的例外。
3. 超限响应：429 `{"error":"too many requests"}`，**没有 `Retry-After` 头**。
4. **fail-open**：Redis 不可用或计数报错 → **直接放行**。限流是护栏，不是门票。

> **提示**：想换成滑动窗口或令牌桶属于"改进项"，不是本阶段任务——那会让窗口交界处的 429 序列与参考实现对不上。

**通过标志**：单测三条绿——窗口内第 11 次登录被拒；Redis 停掉 → 放行；未登录账号维度取不到 subject → 放行。

## 第 4 步 · 错误契约与空集合审计

全项目扫一遍输出 `null` 集合与手写 JSON 的地方，两条铁律补齐：

1. 错误 = 状态码 + `{"error": "文案"}`，全项目只有这一种形状。文案建议逐条对照参考实现的字面量——
   一个实用技巧：**别手抄文案**，直接从原版源码抓一份清单当断言语料（我已用它对这套文档做过全量对账）：

   ```bash
   cd ../feedsystem_video_go-main/backend
   grep -rhoE '"(error|message)": "[^"]+"' --include=*.go internal | sort -u    # 全部字面量文案
   grep -rn -B1 '"error": "' --include=*.go internal        # 每条文案连上一行，直接看到状态码
   grep -rhoE 'errors\.New\("[^"]+"\)' --include=*.go internal | sort -u        # service 层的普通错误
   ```

   三条命令的输出加起来就是原版的完整契约文案集（本机实测：文案 56 条、service 层普通错误 52 条；
   第二条命令输出的是"文案 + 上一行调用点"，行数会多于调用点数，不要求数出某个精确值）；第一行显示 400/500 混在一起是正常的——
   `apierror.ClassifyHTTPStatus` 只认 4 类哨兵错误（401/400/404/200），其余一律 500。
2. 空集合必须序列化成 `[]` 而不是 `null`。逐个写断言的位置：`video_list`、comments、likes、messages、
   followers、vloggers、notifications、uploaded_chunks。

状态码分类只有 **4 个分支**，业务错误默认 500。按你在《03》第 4 步选定的路线（A 照抄 / B 修正），
确认**全项目只有一种策略**，别混用。

**通过标志**：`grep -rn 'null' --include=*.java src/main/java | grep -i list` 之类的人工扫查没有新发现；
第 8 步的自测矩阵里"空集合"断言全部通过。

## 第 5 步 · 观测面与优雅停机（这些配置留到现在才加）

`src/main/resources/application.yml` 追加（`server:` 与 `spring:` 都已存在，**把这几行并进原有块里**；
`management:` 是新开的顶层键，与 `spring:` 平级）：

```yaml
server:
  shutdown: graceful          # 收到退出信号后先处理完在途请求

spring:
  lifecycle:
    timeout-per-shutdown-phase: 2s

management:
  endpoints:
    web:
      exposure:
        include: health,metrics
```

四条事实：

- `GET /healthz` → **无条件** 200 `{"status":"ok"}`，不探测任何依赖（《02》第 5 步写的）；
  保留这个自研端点，**别用 actuator 路径顶替它**。
- actuator 只暴露两个端点组：`management.endpoints.web.exposure.include=health,metrics`。
- 参考实现另开 pprof 端口（API :6060 / Worker :6061，路径 `/debug/pprof/*`）做性能取样；
  Java 侧的定位是 actuator `/actuator/metrics` 打底，需要剖析时用 JFR / `jcmd`。
  练习：压测中两边各抓一份 CPU 剖析，看各自能得出什么结论。
- 日志：参考实现没有级别概念（一行行裸打印）；Boot 默认 logback，给降级路径打 WARN、消费失败打 ERROR——
  **记进差异清单**，这是免费改进。

**通过标志**：`curl -s --noproxy '*' localhost:8081/actuator/health` 返回 200；
`Ctrl-C` 停进程时日志出现 graceful shutdown 且不丢在途请求。

## 第 6 步 · 自测矩阵（本阶段的真正验收）

按行写断言（MockMvc 或 RestAssured），**每个接口成功 + 失败路径各一条**：

| 模块 | 成功路径断言 | 失败路径断言 |
|------|--------------|--------------|
| 账号 | 注册 → 登录 → 刷新 → 改名 → 登出全链，键集合与文案逐字 | 密码错、重名、登出后旧 token 失效 |
| 视频 | 分块 init/upload/status/complete → 发布 → getDetail | 缺字段 400、越权 403、`video not found` |
| 评论点赞 | 发评论、@ 人、列表正序、like/unlike 计数联动 | `video not found`、非作者删评论 401、重复赞文案 |
| 社交与 Feed | 关注后进关注流；五种流各翻 3 页 id 不重不漏 | 关注自己、重复关注、只传一个游标字段 400 |
| 通知私信 | SSE 收帧、list / markRead / unreadCount、私信双向 list | 无 token → 401 `missing token`、空 body markRead 仍 200 |
| Kafka 异步 | 点赞 200 → 毫秒级落库、计数恰好；积压回放全部消费 | broker 停 → 同步降级仍 200；毒消息进 `<topic>.dlq` |
| 限流 | 额度内全部 200 | 第 11 次登录 429 `{"error":"too many requests"}`、无 Retry-After |
| 缓存与降级 | `FLUSHDB` 后全站 200（走 DB） | Redis 挂 → 限流 fail-open、详情与 Feed 全部降级 |

最后一步是全停：把 MySQL / Redis / Kafka 全 `docker compose stop`，`/healthz` 仍返回 200 `{"status":"ok"}`。

**通过标志**：矩阵全绿 + 全停时 `/healthz` 200。

## 第 8 步 · 选修：与参考实现（8080）的差分验收

前提是两版**同时在线**且共享同一套 MySQL / Redis / Kafka：
容器只用你 `deploy/` 这一份；参考实现只用它的**进程**（API + Worker，:8080），
用 `CONFIG_PATH=configs/config.compose-local.yaml` 连到你 3307/6379 的容器上。开测前记三条规则：

1. **同账号互踢**：token 白名单共享 → 一个测试账号只给一版用（`go_u*` / `java_u*` 分开建号）。
2. 共享存储意味着写 A 的数据 B 可见——这正好让"交叉读写"用例成为可能。
3. **限流计数器共享**，压测额度按两边合计算。

脚本放 `feed-java/diff-test/`（bash + curl + jq，或 Python requests）：同一请求发两版 →
归一化（替换动态 id、时间戳、upload_id、Host）→ diff → 输出通过 / 失败报告。场景清单：
D1 账号全链；D2 业务错误文案；D3 上传发布统计；D4 五种流各翻 3 页（匿名 + 登录）；
D5 `FLUSHDB` 冷启动自愈；D6 热榜快照冻结；D7 分块跨实现接力；D8 停 broker 走同步降级；
D9 SSE 跨进程收不到（《08》的架构事实）；D10 限流跨两版累计到第 11 次、两边同 429。
每做完一条给个结论：一致 / 已修平 / 豁免（必须写理由，它同时就是差异清单的素材）。

前端终验：把 vite proxy 指向 8081，以真实用户身份玩 15 分钟——刷推荐流 / 关注流 / 热榜、
播放并拖进度条（验 Range）、上传 30 MB 视频并在 50 % 时刷新（验续传）、评论 @ 好友、
发私信、看通知红点；DevTools 的 Network / Console 全程无报错。

> **说明**：差分不是验收的必要条件，第 6 步的自测矩阵才是；这步用来量化"我还欠多少行为兼容"。

## 卡住了看这里

**限流测试时 8081 已经 429，8080 却还放行。**
原因：不是 bug，是同一个计数器的竞读时序；也可能是两边 IP 取值不同（XFF）。
处理：先 `cd deploy && docker compose exec redis redis-cli --no-auth-warning -a 123456 GET feedsystem:ratelimit:account_login:127.0.0.1`，确认是不是同一个 key 再谈行为。

**D4 偶尔 id 序列不同。**
原因：两版读同一 ZSET 时恰好有写流量在点赞 / 发布。
处理：差分期间冻结写流量（用例串行），或先比集合再单独立一个"顺序敏感"用例。

**ab 压测第一轮 P95 极差。**
原因：JIT 冷启动。
处理：正式采样前先跑一轮预热，并在报告里注明采样方法。

**矩阵里某些断言 400、某些 500，同一类错误两种码。**
原因：《03》选的状态码策略在个别模块没落地（混用）。
处理：回到第 4 步的"只有一种策略"，按选定路线统一；改动记进差异清单。

**改了 vite 的 proxy 忘改回来，参考实现看起来"坏了"。**
原因：前端流量被指去了 8081。
处理：用 `VITE_API_TARGET` 环境变量化（见第 9 步），从此两版一键切换——这十行值得写。
