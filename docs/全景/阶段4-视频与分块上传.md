## 2. 文件落盘与访问

```mermaid
%%{init: {"flowchart": {"curve": "linear"}}}%%
flowchart LR
    FS[["data/uploads"]] --> AV["avatars/{uid}/{32hex}.{ext}"]
    FS --> CV["covers/{uid}/{yyyyMMdd}/{32hex}.{ext}"]
    FS --> VD["videos/{uid}/{yyyyMMdd}/{32hex}.mp4"]
    FS --> TP["tmp/{uploadId}/{index}（纯数字）"]

```

- 文件名是 **16 字节随机 hex**（防重名、防路径穿越）；视频/封面按天分目录。
- `tmp/` 放分块临时片，合并成功后删除；`avatars`/`videos`/`covers` 带日期的是视频与封面，头像不带。
- 线上 URL 一律走 `/static/**`（阶段 2 的映射），磁盘根目录与 URL 前缀是**映射关系**不是同名关系。

## 3. 发布：一个事务四步

```mermaid
sequenceDiagram
    participant C as 客户端
    participant VS as VideoService
    participant DB as MySQL

    C->>VS: POST /video/publish {title, description, play_url, cover_url}
    VS->>VS: trim 校验三个必填（空 → 500，不是 400）
    VS->>DB: 查 accounts 取用户名快照
    Note over VS,DB: ── @Transactional ──
    VS->>DB: ① insert videos
    VS->>DB: ② insert outbox_msgs(video_published, pending)
    VS->>VS: ③ 抽 #话题并去重
    VS->>DB: ③ insert ignore tags → 回查 id
    VS->>DB: ④ insert video_tags 关联
    Note over VS,DB: ── 提交 ──
    VS-->>C: 整个 Video JSON（含 id、RFC3339 create_time）
```

三个要点：

- **必填缺失是 500 不是 400**（契约如此，与账号阶段相反）。
- `description` **不做 trim**，原样入库。
- `outbox_msgs` 与视频**同事务**写（本地消息表模式）：阶段 7 的 Kafka 消费者扫 `pending` 投递后删行，现有 3 行存量就是给它准备的。
- `videos.username` 是发布时的**用户名快照**，发布时从 `accounts` 查。

## 4. 详情读：缓存 + 锁 + 轮询

```mermaid
%%{init: {"flowchart": {"curve": "linear"}}}%%
flowchart LR
    A["getDetail(id)"] --> B{"读缓存"}
    B -->|"命中"| C["返回（TTL 5 分钟）"]
    B -->|"未命中"| D{"抢锁 SET NX PX 2000"}
    D -->|"抢到"| E["double check 再读缓存"]
    E -->|"有"| C
    E -->|"没有"| F["查库"]
    F -->|"查无"| G["404 record not found"]
    F -->|"有"| H["写缓存并返回"]
    H --> I["finally：Lua 按 token 释放锁"]
    D -->|"没抢到"| J["每 20ms 轮询缓存，最多 5 次"]
    J -->|"读到"| C
    J -->|"没读到"| K["直查库，但不写缓存"]

    classDef err fill:#fdecea,stroke:#c62828
    class G err
```

| 机制 | 解决什么 |
|---|---|
| 缓存 TTL 5 分钟 | 热点视频重复读不落库 |
| 锁 TTL 2 秒 + Lua 按 token 释放 | 只让一个线程回源（防击穿）；持锁者崩溃锁自动过期；Lua 避免误删别人的锁 |
| double check | 抢锁瞬间前一个持锁者可能刚写完缓存 |
| 20ms×5 轮询 | 没抢到锁的请求等一下，能等到就不用自己查库 |
| 等不到**不回填** | 防止迟到的非持锁者覆盖持锁者刚写的版本 |
| 异常一律降级 | Redis 异常只记日志、直查库 → 缓存挂了不影响功能 |

**热度缓存 `updatePopularityCache`**：已定义、**还没有调用者**——阶段 5 的点赞第一次调用它
（删详情缓存键 + `ZINCRBY` 热度窗口键）。这是本阶段给阶段 5 留的接口。

## 5. 分块上传

### 两个 Redis 键

| 键 | 值 | 作用 |
|---|---|---|
| `v1:chunk_upload:{uploadId}` | 会话 JSON（含 `uploaded_bits` 位图） | **唯一事实来源**，进度只看它 |
| `v1:chunk_upload_hash:{uid}:{fileHash}` | 裸 uploadId（不是 JSON） | 续传索引：同一文件哈希可找回旧会话 |

都 24 小时 TTL（未完成的上传自动过期，不需要清理任务）。
选 Redis 不建表的原因：24 小时瞬时状态、位图高频小写（免行锁与事务开销）、位图即事实来源、丢了重传即可。

### 四个端点

```mermaid
%%{init: {"flowchart": {"curve": "linear"}}}%%
flowchart LR
    INIT["chunk/init<br/>五字段校验 + 200MB 上限<br/>hash 命中 → 续传（同 upload_id）<br/>未命中 → 新建"]
    UP["chunk/upload<br/>校验后落盘 tmp/{uploadId}/{index}<br/>置位图回写会话"]
    ST["chunk/status<br/>upload_id + 已传下标 + 总片数"]
    CP["chunk/complete<br/>位图不满 → 400<br/>满 → 按 0..N-1 拼接<br/>→ videos/，清 tmp + 删两键"]
    INIT --> UP --> CP
    ST -.->|"随时查进度"| UP
```

### `upload` 的校验顺序（顺序本身就是契约）

```mermaid
%%{init: {"flowchart": {"curve": "linear"}}}%%
flowchart LR
    A{"会话存在?"} -->|"否"| E1["404 upload session not found"]
    A -->|"是"| B{"属主一致?"}
    B -->|"否"| E2["403 forbidden"]
    B -->|"是"| C{"下标越界?"}
    C -->|"是"| E3["400 invalid chunk_index"]
    C -->|"否"| D{"该位已置位?"}
    D -->|"是"| OK["200 {chunk_index:n}<br/>幂等，早于 file 检查"]
    D -->|"否"| F{"带了 file?"}
    F -->|"没有"| E4["400 missing file"]
    F -->|"有"| G{"MD5 等于 chunk_hash?"}
    G -->|"否"| E5["400 chunk hash mismatch<br/>+ expected/actual"]
    G -->|"是"| H["写盘 + 置位图 → 200"]
```

两个反直觉点（契约如此）：

1. **幂等判断早于 file 检查**：已传过的下标重传，连 `file` 都不带也返回 200，响应体与首次上传完全一样。
2. **`expected`/`actual` 与字面相反**：`expected` = 客户端传来的 `chunk_hash`，`actual` = 服务端算出的 MD5。

### `complete` 的合并与清理

```mermaid
%%{init: {"flowchart": {"curve": "linear"}}}%%
flowchart LR
    A["位图满"] --> B["建目标文件（CREATE + APPEND）"]
    B --> C["i = 0..N-1 依次拷分片"]
    C --> D{"全部成功"}
    D -->|"是"| E["删 tmp + 删两键<br/>返回 url / play_url"]
    D -->|"否"| F["删半成品<br/>tmp 与两键保留<br/>可重传后重试"]
    classDef ok fill:#e7f6ec,stroke:#2e7d32
    classDef err fill:#fdecea,stroke:#c62828
    class E ok
    class F err
```

- `missing` 是**缺片个数、封顶 5**（不是缺片下标列表）：7 片全不传 → `{"missing":5,"completed":0,"total":7}`。
- 失败时保留 tmp 与两键，是为了「补传缺片后重试」——这是断点续传语义的一部分。

### Redis 是硬依赖（与详情缓存相反）

| 场景 | 行为 |
|---|---|
| 详情缓存 Redis 挂了 | **降级**：直查库、不写缓存，功能照常 |
| 分块 Redis 挂了 | **503** `chunk upload requires redis`（四端点统一） |

判定分两层：启动探活失败 → `FeatureFlags.cacheEnabled()` 为 false（四个方法第一行过 `requireCache()`）；
运行中挂掉 → `ChunkSessionStore` 捕获 `DataAccessException` → 503。
